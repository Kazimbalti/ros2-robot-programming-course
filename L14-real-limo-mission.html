14.0Safety first

⚠️ Six rules. Every team member reads them aloud before the robot is switched on.
  1. Floor only. Never run motion code with the robot on a table.
  2. One safety officer per team stays next to the robot, ready to lift it or switch it off. The safety officer does not type.
  3. Slow first. Max 0.2 m/s and 0.5 rad/s until the code is proven.
  4. Have the stop command ready in its own terminal (below) before starting any node.
  5. Clear area: no bags, cables or feet in the arena.
  6. Battery: stop and charge when the LIMO reports low battery; never leave it charging unattended.
💻 The "stop" terminal: keep it open, press ↑ Enter to use it
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist "{}"
🛑 Make your nodes stop the robot when you press Ctrl+C

In simulation a watchdog stopped the LIMO for us. On real hardware, don't rely on it: make every node that publishes /cmd_vel send a zero command on exit. Change the main() of go_to_goal.py, drive_square.py, wanderer.py and red_follower.py to:

📄 safe main() for any driving node
def main(args=None):
    rclpy.init(args=args)
    node = GoToGoal()                         # your node class
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.cmd_pub_.publish(Twist())        # zero velocity = stop
        node.destroy_node()
        rclpy.try_shutdown()

14.1The idea: sim → real

✅ What stays the same

  • The topics: /cmd_vel, /odom, /scan, /imu, and the camera.
  • Your nodes: they use angles and topic names, not Gazebo.
  • All the tools: ros2 topic, RViz, TF, bags, launch files.

⚠️ What changes

  • No simulation time: remove use_sim_time:=true!
  • Noise: LiDAR ranges jitter, and shiny or black surfaces return nothing.
  • Slip: odometry drifts more on smooth floors.
  • Lighting: HSV thresholds need re-tuning under lab lights.
  • Delay and battery: Wi-Fi lag; the robot slows as the battery drops.

L1Lab 1 — Meet and bring up the LIMO

LAB 1 · 40 min

Connect, start the drivers, drive by keyboard

1Switch on and connect over SSH

Put the LIMO on the floor, switch it on and wait about a minute. Your laptop/VM must be on the same Wi-Fi as the robot. The IP address and login are on the robot's label.

💻 Laptop terminal
ping -c 3 <LIMO_IP>
ssh agilex@<LIMO_IP>

You are now typing on the robot's computer. Every robot terminal needs its own ssh. Terminator split panes make this easy.

2Bring up the base, LiDAR and TF
💻 Robot terminal 1 (via ssh)
ros2 launch limo_bringup limo_start.launch.py
💻 Robot terminal 2 (via ssh)
ros2 topic list
ros2 topic hz /scan
ros2 topic echo /odom --field pose.pose.position

✅ Compare with the simulator (Lecture 8, Lab 1): the same key topics are there. Push the robot gently by hand: does /odom change?

3Drive by keyboard (safety officer ready)
💻 Robot terminal 3 (via ssh)
ros2 run teleop_twist_keyboard teleop_twist_keyboard

Press z several times first to slow down. Drive 1 m forward with a tape measure on the floor, and compare the real distance with /odom. Write both down: this is your first sim-to-real measurement.

4(Optional) See the robot from your laptop

If your laptop runs the same ROS 2 distro as the robot, you can use RViz on the laptop. Both sides must use the same ROS_DOMAIN_ID (on the robot's label), and each team a different one:

💻 Laptop terminal (and robot, if not already set)
export ROS_DOMAIN_ID=<TEAM_NUMBER>
ros2 topic list
rviz2 -d ~/ros2_ws/limo.rviz

No topics from the robot? The network may block discovery, or the distros differ. That's fine: use option A in Lab 2 and run everything on the robot.

L2Lab 2 — Your code on the real robot

LAB 2 · 60 min

limo_lab goes live

1Option A (always works): copy and build your package on the robot
💻 Laptop terminal
ssh agilex@<LIMO_IP> "mkdir -p ~/team<N>_ws/src"
scp -r ~/ros2_ws/src/limo_lab agilex@<LIMO_IP>:~/team<N>_ws/src/
💻 Robot terminal (via ssh)
cd ~/team<N>_ws
colcon build --packages-select limo_lab --symlink-install
source install/setup.bash

Use your team's own workspace, never the robot's system workspace. Option B: if Lab 1 step 4 worked, you can instead run nodes on your laptop and they drive the robot over Wi-Fi.

2Read-only first: odometry and the nearest obstacle
💻 Robot terminal (note: NO use_sim_time)
ros2 run limo_lab odom_reader
ros2 run limo_lab nearest_obstacle

Walk around the robot. Does nearest_obstacle find your legs, with the correct LEFT/RIGHT? Your code uses angles, not fixed indices, so it works even if the real LiDAR's range differs from the simulator's.

3Closed loop on the floor: go_to_goal
💻 Robot terminal
ros2 run limo_lab go_to_goal --ros-args -p goal_x:=1.0 -p goal_y:=0.0

Mark the start and the goal with tape. Measure the real final error with a ruler. Does it match the "final error" the node reports? The difference is odometry error, which is why Lectures 12–13 use a map.

4Reactive on the floor: the wanderer
💻 Robot terminal
ros2 run limo_lab wanderer --ros-args -p speed:=0.12 -p safety_distance:=0.5

Build a small arena from boxes. Does it behave like in Gazebo? Note every difference in your logbook: that's the sim-to-real gap.

14.2The final mission: "LIMO Delivery"

Final project · teams of 3–4 · simulation or real robot

Deliver, inspect, report

The LIMO starts at the Home position of a mapped arena. It must, by itself:

  1. Navigate to Station A and Station B (waypoints) without touching anything.
  2. At Station C, search for the red object with the camera, turn to face it, and stop 30–50 cm in front of it.
  3. Return Home.
  4. During the whole mission, publish your progress on a topic /mission_status (std_msgs/msg/String, e.g. "Going to A", "Red object found", "Mission complete").

Hint: a clean structure

One mission_manager.py node (it uses a BasicNavigator) runs the steps in order. For Station C: after goToPose(C) succeeds, it hands control to your red-follower logic (subscribe to /red_target, publish /cmd_vel) until the blob area is big enough, then calls goToPose(Home). A launch file mission.launch.py starts color_tracker (with show_window: False) and mission_manager, with waypoints as parameters.

Deliverables

  • Your limo_lab package on GitHub (with a README: how to launch).
  • A 2–3 minute video of one full, unedited run.
  • A ros2 bag of that run (/odom /cmd_vel /scan /mission_status).
  • A one-page report: your node graph (rqt_graph), what went wrong, and 3 sim-to-real differences you measured.

✅ Knowledge checkLecture 14 check: 5 questions

What is the first thing you do before running any motion node on the real LIMO?

Safety first: be ready to stop the robot at any moment.

Your node runs on the real robot but nothing happens. The most likely cause?

There is no /clock on a real robot.

Two teams see each other's topics. Fix?

Different domain IDs separate ROS 2 networks.

go_to_goal reports a 3 cm error, the ruler says 15 cm. Why?

Exactly what you measured in Lecture 12 Lab 1.

Why make every driving node publish a zero Twist in finally:?

Many real drivers keep executing the last command they received.

14.3When things go wrong · Reflection

You see…WhyFix
ssh: connection timed outNot on the robot's network, or wrong IP.Check Wi-Fi; ping the IP; ask for the label.
Node runs but the robot doesn't moveuse_sim_time:=true left on (no /clock on a real robot, so timers never fire).Remove it.
Laptop sees another team's robotSame ROS_DOMAIN_ID.Each team uses its own number, on both sides.
Robot keeps driving after Ctrl+CThe driver holds the last command.Use the stop terminal now; add the safe main() to your nodes.
Red detection fails in the labReal lighting differs from Gazebo.Print HSV values of the object; widen the S/V ranges.
Nav2 drifts off the mapBad initial pose, or a featureless arena.Re-do 2D Pose Estimate; add boxes to give the LiDAR features.

Name three things that are identical between the Gazebo LIMO and the real LIMO from your code's point of view.

Answer
Topic names (/cmd_vel, /odom, /scan), message types (Twist, Odometry, LaserScan), and the TF frame names. That's why your nodes run on both.

Why must you remove use_sim_time on the real robot?

Answer
Nothing publishes /clock, so a node on sim time sees time frozen at 0 and its timers never fire.

Your go_to_goal reports a 3 cm error but the ruler says 15 cm. What's the explanation, and what's the fix?

Answer
The controller trusts odometry, which drifted (wheel slip). The fix is localisation against a map (AMCL, Nav2), which corrects map → odom.
