3.1Workspace — The Project's Factory

In Lecture 2 you launched LIMO in Gazebo and watched Topics and TF frames appear without worrying too much about where any of it lived on disk. Now we open the hood. Every piece of ROS 2 code you write or run — the URDF that describes LIMO's body, the launch files that start Gazebo, the node that will eventually drive the robot around a warehouse — lives inside a workspace. Understanding this folder structure properly is the difference between "I typed the commands and it worked" and "I know exactly what happened when I typed the commands."

📖 Definition: Workspace

A workspace is the top-level folder that holds all of a project's ROS 2 packages, the intermediate files produced while building them, and the final runnable output. A single LIMO project — say ~/limo_ws — typically holds every package you need: the robot description, the Gazebo simulation, the custom messages, and your own lab code, all side by side.

Every ROS 2 workspace, once built at least once, has exactly four top-level folders:

limo_ws/
├── src/       # your source code — packages you write or clone
├── build/     # intermediate compilation artifacts (scratch space)
├── install/   # the final, runnable product of the build
└── log/       # build and run reports
FolderRoleDo you edit it by hand?
src/Home of every package: URDF, launch files, Python/C++ nodes, message definitionsYes — almost all of your work happens here
build/Scratch space colcon uses while compiling each packageAlmost never — safe to delete and rebuild
install/The finished, runnable product — this is what gets sourcedOnly to source setup.bash
log/Detailed text logs of every colcon build and diagnostic outputOnly when a build fails and you need to see why
🧠 Analogy: The Factory Floor

src is the design office where engineers draft blueprints. build is the assembly line — messy, full of half-finished parts, and nobody ships from there. install is the warehouse: only finished, tested products get shelved there, and that's the only place a customer (your terminal, running ros2 run) is allowed to pick something up from. log is the factory's incident ledger — when something on the line goes wrong, you go read the log, not guess.

This is exactly why, after every colcon build, you must source install/setup.bash again: you are telling the current terminal session where the warehouse is. Skip this step and ROS 2 behaves as if the package you just built doesn't exist, even though the files are sitting right there in install.

🌍 In the Real Course

For this lecture series you'll work almost entirely inside one shared workspace — something like ~/limo_ws/src/KV6022_limo_ros2 — which already bundles the robot description, the Gazebo simulation, custom messages, teaching examples, and the capstone assessment package as siblings under one src folder. This mirrors how real robotics teams work: one workspace per robot platform, many packages inside it, each with a narrow job.

3.2Package — The Buildable Unit

If the workspace is the factory, a package is one production line inside it — the smallest unit ROS 2's build tool understands and compiles independently. A LIMO project is never one giant folder of files; it's split into focused packages, each responsible for one concern.

📖 Definition: Package

A package is the smallest organized, independently buildable unit in ROS 2. It can contain nodes, launch files, URDF/xacro models, message definitions, RViz configs, parameter files, and tests — but it always declares its own identity and dependencies through a package.xml file at its root.

Every package has an identity card and a build recipe. Which recipe it uses depends on its build type:

Build typeLanguageExtra files
ament_pythonPython nodessetup.py (entry points) + setup.cfg
ament_cmakeC++ nodes, or pure data/description packagesCMakeLists.txt

A quick way to check which kind a package is, without opening every file:

grep build_type package.xml
# <build_type>ament_python</build_type>   → Python package, has setup.py
# <build_type>ament_cmake</build_type>    → C++ or description package, has CMakeLists.txt

For an ament_python package, setup.py contains an entry_points block that maps a human-friendly runnable name to a Python module and function — this is exactly what makes ros2 run my_package my_node work. We'll dissect a real one in section 3.4.

⚠️ Package ≠ Node

Don't collapse these two ideas. A workspace can hold many packages, and a single package can hold many nodes — limo_gazebosim, for example, holds four separate launch files, one per drive mode, but no node code of its own. Keep each package's job narrow; a package that tries to do everything becomes impossible to reuse or test in isolation.

Each of the four commands has a distinct job, now that you know the vocabulary:

CommandWhat it actually does

rosdep install ...Reads every package's package.xml dependency list and installs the missing system libraries (e.g. gazebo_ros)

🧠 Why --symlink-install?

Without it, colcon build copies your Python files from src into install. Edit a node afterward and nothing changes at run time — you're still running the stale copy — until you rebuild. With --symlink-install, colcon creates a symbolic link instead of a copy for Python files, so edits in src take effect immediately on the next ros2 run, no rebuild needed. It costs nothing and saves you from a very confusing class of "why isn't my change showing up" bugs, so make it a habit for every LIMO workspace you build.

⚠️ Building Just One Package

As the workspace grows across the course, rebuilding all six packages every time gets slow. Once you're only touching one package, scope the build: 

colcon build --packages-select example_codes --symlink-install

This still requires re-sourcing if it's a new terminal, but it skips recompiling everything else.

3.4Your First Real LIMO Controller Node

Time to write code that actually moves the robot. We'll create a brand-new package for this week's lab, write a node that publishes velocity commands on a timer, register it as a runnable executable, build it, and run it against the simulated LIMO from Lecture 2.

Step 1 — Create the package

student@limo:~/limo_ws/src$ ros2 pkg create --build-type ament_python week3_lab --dependencies rclpy geometry_msgs going to create a new package package name: week3_lab destination directory: /home/student/limo_ws/src package format: 3 version: 0.0.0 description: TODO maintainer: ['student <student@todo.todo>'] licenses: ['TODO: License declaration'] build type: ament_python dependencies: ['rclpy', 'geometry_msgs'] creating folder ./week3_lab creating ./week3_lab/package.xml creating ./week3_lab/setup.py creating ./week3_lab/setup.cfg creating folder ./week3_lab/resource creating ./week3_lab/week3_lab/__init__.py creating folder ./week3_lab/test

--dependencies rclpy geometry_msgs automatically writes the right <depend> tags into package.xml — no manual editing needed for those two.

Step 2 — Write the node

Create week3_lab/week3_lab/command_publisher.py:

import rclpy
from rclpy.node import Node
from geometry_msgs.msg import Twist


class CommandPublisher(Node):
    def __init__(self):
        super().__init__('command_publisher')
        self.publisher_ = self.create_publisher(Twist, '/cmd_vel', 10)
        self.timer_period = 0.5  # seconds
        self.timer = self.create_timer(self.timer_period, self.timer_callback)
        self.get_logger().info('command_publisher started — publishing to /cmd_vel every 0.5s')

    def timer_callback(self):
        msg = Twist()
        msg.linear.x = 0.15    # drive forward at 0.15 m/s
        msg.angular.z = 0.2    # gentle left turn
        self.publisher_.publish(msg)
        self.get_logger().info(
            f'Publishing: linear.x={msg.linear.x:.2f}  angular.z={msg.angular.z:.2f}'
        )


def main(args=None):
    rclpy.init(args=args)
    node = CommandPublisher()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()


if __name__ == '__main__':
    main()
🧠 Reading This Node

Nothing here is new machinery from Lecture 2 — it's the same publisher + timer pattern applied to a real topic. create_publisher(Twist, '/cmd_vel', 10) opens a publisher on the exact topic every LIMO drive mode listens to, with a queue depth of 10. create_timer(0.5, ...) calls timer_callback twice a second for as long as rclpy.spin(node) keeps the node alive. Every drive mode you'll meet in section 3.5 is, underneath, just something subscribed to this same /cmd_vel topic.

Step 3 — Register it as a runnable executable

Open setup.py and edit the entry_points block:

entry_points={
    'console_scripts': [
        'command_publisher = week3_lab.command_publisher:main',
    ],
},
PartMeaning
command_publisher (left side)The name you'll type after ros2 run week3_lab
week3_lab.command_publisherThe Python module path: week3_lab/week3_lab/command_publisher.py

With a differential-drive LIMO already spawned in Gazebo from Lecture 2, this node alone is enough to make it roll forward in a gentle curve — the same principle every teleop tool, navigation stack, and autonomy pipeline you'll build for the rest of the course ultimately relies on.

🛠️ On the Physical LIMO

Everything in this section runs unmodified against the real robot. Swap the simulated LIMO for the physical chassis over SSH and the same ros2 run week3_lab command_publisher drives it — /cmd_vel is the same interface either way. Always test new controller nodes in Gazebo first; a 0.15 m/s bug in simulation is a shrug, the same bug on hardware is a robot rolling off a table.

3.5LIMO's Four Drive Modes, Conceptually

Here is the fact that makes LIMO special as a teaching platform: it is not one robot but four, sharing a single chassis footprint and a single command interface. AgileX ships four separate xacro assemblies — one per physical drivetrain — and every one of them is built from the same shared macro library in limo_properties.xacro (limo_wheel, limo_mecanum_wheel_1/2, limo_left_steering_hinge, limo_right_steering_hinge, limo_laser, limo_depth_camera, limo_imu). What differs between modes is purely which macros get assembled and how the wheel joints are defined.

Let's look at what's actually different in each xacro file.

1. Differential — limo_diff.xacro

The classic setup: two pairs of drive wheels (left pair, right pair) joined to the chassis by continuous joints — free-spinning, no angle limit. Steering is done entirely by spinning the left and right pairs at different speeds. Because there's no separate steering geometry, differential LIMO can rotate on the spot: a zero turning radius.

2. Ackermann — limo_ackerman.xacro

The front wheels are no longer rigidly mounted — each connects through a revolute steering_hinge joint (limo_left_steering_hinge / limo_right_steering_hinge), with rotation axis 0 0 ±1, limited to ±0.523598767 rad (≈ ±30°), effort limit 1000, velocity limit 1.0, zero joint damping and 2.0 friction. The rear wheels stay simple continuous drive joints, exactly like the differential mode. This is a real car-like steering geometry: LIMO can no longer spin in place, and it has a minimum turning radius set by that ±30° hinge limit. 

<joint name="left_steering_hinge_joint" type="revolute">
  <axis xyz="0 0 1"/>
  <limit lower="-0.523598767" upper="0.523598767"
         effort="1000" velocity="1.0"/>
  <dynamics damping="0.0" friction="2.0"/>
</joint>

3. Mecanum — limo_mecanum.xacro

All four wheels are replaced with Mecanum rollers using the limo_mecanum_wheel_1 and limo_mecanum_wheel_2 macros — distinct front-left/front-right meshes, since the diagonal roller pattern is mirrored between the two sides and baked directly into the .dae mesh geometry. Each wheel is driven independently, and the combination of four independently-controlled angled rollers gives LIMO full holonomic freedom: it can strafe sideways or move diagonally without rotating its heading first.

4. Tracked — limo_track.xacro

Wheels are replaced entirely by continuous rubber tracks. Like the differential mode, steering comes from driving the left and right tracks at different speeds — but the much larger ground-contact area and friction give dramatically better traction on loose or uneven terrain, at the cost of a less crisp pivot (the tracks scrub and drag against the ground during a turn rather than rotating cleanly like wheels).

📖 Definition: Holonomic vs. Non-Holonomic

A holonomic drivetrain can move instantaneously in any direction on the ground plane — Mecanum LIMO can strafe sideways without turning. A non-holonomic drivetrain is constrained: it can only move along directions its wheels currently allow — differential, Ackermann, and tracked LIMO must all rotate (or, for Ackermann, arc) before they can translate sideways.

🔧 One Topic, Four Interpretations

Every mode's ros_control plugin subscribes to the same /cmd_vel (geometry_msgs/msg/Twist) topic — the exact topic your command_publisher node from section 3.4 already publishes to. What changes between modes is purely how linear.x and angular.z get converted into wheel motion — and for Mecanum only, linear.y is also honored, since it's the one mode that can actually move sideways. This is a deliberate design choice: your controller code from section 3.4 doesn't need to change at all to drive any of the four modes.

⚠️ Only Ever Run One Drive-Mode World at a Time

Each launch file starts its own gzserver, its own robot_state_publisher, and publishes to the same names (/cmd_vel, /tf, /scan). Launching a second drive mode before shutting down the first (Ctrl+C, and wait for the process to actually exit) causes duplicate node name errors, TF conflicts between two competing robot models, and a /cmd_vel that's being interpreted by two different drivetrains simultaneously. Always fully close one world before opening the next.

To sanity-check the TF tree and URDF for whichever mode is currently running, open the shipped RViz config:

rviz2 -d ~/limo_ws/src/KV6022_limo_ros2/src/limo_gazebosim/rviz/urdf.rviz

This is the rviz config shipped inside limo_gazebosim/rviz/ — it's pre-configured to show the robot model and TF frames, so you can visually confirm the front wheels are actually hinged in Ackermann mode, or that all four wheels are independent in Mecanum mode.

🧠 What to Actually Feel For
  • Differential: hold the turn-in-place key — the robot rotates around its own center, never translating.
  • Ackermann: try the same turn-in-place key — nothing happens (or barely anything); you must be moving forward to turn at all, and the arc is wide.
  • Mecanum: use the strafe key — the robot slides sideways while facing the same direction the whole time.
  • Tracked: turn in place like differential, but notice the motion feels heavier and less crisp — that's the tracks scrubbing against the ground.

3.7Choosing a Drive Mode for a Real Task

In a real deployment you don't pick a drive mode because it's fun to try — you pick it because it fits the environment. Since all four modes share the same chassis, sensors, and /cmd_vel interface, the choice is purely about the physical task in front of the robot.

🌍 Matching Mode to Environment
  • Tight warehouse aisles, parking between shelves: Mecanum — the ability to strafe sideways and slide into a slot without a three-point turn is decisive when floor space is scarce.
  • Outdoor paths, road-following, campus delivery: Ackermann — its car-like turning geometry is the most realistic match for structured, road-like environments, and its steering behavior directly resembles what students will meet later with real autonomous vehicles.
  • Uneven, loose, or outdoor rough terrain: Tracked — maximum ground contact and traction wins over turning precision when the surface itself is the main challenge.
  • General-purpose lab or classroom use: Differential — mechanically the simplest, cheapest to maintain, and the easiest to reason about, which is exactly why it's the default mode for most of this course's early exercises.

Notice this is an engineering trade-off, not a hierarchy — Mecanum's holonomic freedom comes at the cost of traction and mechanical complexity (more joints, more rollers, more that can wear out); Ackermann's realism comes at the cost of maneuverability in tight spaces. There's no universally "best" mode, only the one that fits the task.

3.8Summary, Checkpoint, and Glossary

You now understand the machinery beneath every command you've been typing since Lecture 1. A workspace holds packages; packages declare their identity in package.xml and their build type as ament_python or ament_cmake; colcon build --symlink-install turns source into a runnable install tree that must be sourced into every new terminal. You wrote and ran a real controller node — command_publisher — that publishes Twist messages on /cmd_vel, and you saw that this exact same topic is the single entry point every one of LIMO's four drive modes listens on, no matter how differently each one turns that command into wheel motion underneath.

Workspace
The top-level folder (src/build/install/log) holding all of a ROS 2 project's packages and build output.
Package
The smallest independently buildable unit in ROS 2, identified by a package.xml at its root.
entry_points
The section of setup.py in an ament_python package that maps a runnable name to a module:function pair.
colcon
The official ROS 2 build tool; compiles every package under src into build, producing the finished install tree.
ament_python / ament_cmake
The two package build types in ROS 2 — Python packages use setup.py, C++ (or pure-data) packages use CMakeLists.txt.
Holonomic vs. non-holonomic
A holonomic drivetrain (Mecanum) can move in any direction instantly; a non-holonomic one (differential, Ackermann, tracked) is constrained by its wheel geometry.
Ackermann steering
A car-like steering geometry where the front wheels pivot on hinge joints within an angle limit, giving the vehicle a minimum turning radius instead of a zero-radius spin.

Common Mistakes

  • Forgetting --symlink-install on the first build, then editing a Python node and wondering why the change never shows up at run time.
  • Editing or rebuilding a package but forgetting to re-source install/setup.bash in the terminal you're actually running from.
  • Launching a second drive-mode Gazebo world before fully closing the first one, causing duplicate node names and TF/topic conflicts.
  • Mixing up which xacro macro belongs to which mode — remember: limo_left/right_steering_hinge is Ackermann-only, limo_mecanum_wheel_1/2 is Mecanum-only, and differential/tracked both use plain continuous drive joints.
