6.1Gazebo as LIMO's virtual lab

Every session so far has run against either turtlesim or a LIMO whose motion you mostly took for granted. This session opens the hood: what actually makes a simulated LIMO fall under gravity, roll on friction, and bump into a pothole model? The answer is Gazebo Classic 11, driven through the gazebo_ros bridge and a family of gazebo_plugins. This course deliberately uses Gazebo Classic rather than the newer gz-sim (Ignition) line, because Classic 11 is the version that pairs most reliably with ROS 2 Humble in a teaching lab — fewer moving parts, fewer version mismatches, one consistent set of tutorials.

🧠 Simple Analogy

RViz (Lecture 5) is a window — it only shows you what's already been measured or computed. Gazebo is a laboratory: it has an actual physics engine (ODE — Open Dynamics Engine) computing gravity, mass, friction, and collisions at every simulation step, whether or not you're looking. Drop LIMO one metre above the potholes world and in RViz nothing happens; in Gazebo, it falls.

📖 Real-Time Factor (RTF)

RTF = simulation-time-elapsed / wall-time-elapsed. RTF = 1.0 means one second of simulated physics takes exactly one second of your life. RTF < 1 means the simulation is running slower than real time — very common on a modest laptop once you add a detailed world, several pothole meshes, and a LiDAR. Watch RTF in Gazebo's bottom status bar; if it's badly below 1, your /cmd_vel commands and sensor timestamps are all being computed "in slow motion" relative to the wall clock, which can make timing-sensitive code (like our watchdog in 6.4) misbehave if you assumed real-time.

The limo_gazebosim package ships several real worlds, each built for a different purpose:

World fileWhat it containsGood for
simple.worldEmpty ground plane, basic lightingFirst launch, sanity checks, isolating a bug from world complexity
potholes.world / potholes_simple.worldA road surface with pothole models scattered across itThe course's capstone "road defect survey" theme
simulation_table.world, _small, _with_obstaclesA tabletop-scale arena, optionally with obstaclesIndoor navigation practice at a scale that fits a small room

Which world loads is normally set inside the launch file's world argument. If that argument is exposed, you can override it from the command line: 

ros2 launch limo_gazebosim limo_gazebo_diff.launch.py world:=potholes_simple.world

Otherwise, open the launch file and edit the default path to point at the .world file you want under limo_gazebosim/worlds/.

⚠️ Common Trap

A poor RTF is not always your fault. It's a genuine trade-off: complex meshes (pothole geometry, tables, obstacles) cost more physics computation per step. If your simulation feels sluggish, try simple.world first to confirm the controller code itself is fine before blaming your laptop.

6.2How Gazebo actually drives LIMO

In this course's simulation stack, LIMO's Gazebo model carries a gazebo_ros plugin (a differential-drive plugin from the gazebo_plugins family) attached directly to its wheel joints. This single plugin does three jobs at once, and understanding the loop end to end demystifies everything you've been typing since Lecture 2.

flowchart LR A["/cmd_vel
geometry_msgs/Twist"] --> B["gazebo_ros diff-drive plugin"] B --> C["ODE physics engine
wheel velocities / torques"] C --> D["Robot moves in the World"] D --> E["/odom
nav_msgs/Odometry"] D --> F["odom → base_link TF"] style B fill:#eef0ff,stroke:#3d4bf5,color:#211f1a,font-weight:bold style E fill:#eafaf3,stroke:#0e9e6e,color:#211f1a style F fill:#eafaf3,stroke:#0e9e6e,color:#211f1a
  1. The plugin subscribes to /cmd_vel — the same topic you have been publishing to since your very first turtlesim exercises.
  2. It converts that linear/angular velocity into per-wheel commands and hands them to the ODE physics engine, which applies real forces and torques, respecting friction, mass, and collisions.
  3. Every simulation step, the plugin reads back the resulting motion and publishes /odom and broadcasts the odom → base_link TF itself — no separate node needed.
🔧 "Plugin does everything" — good and bad

This is a deliberately simple, direct pattern: one plugin owns input, physics, and output. It's fantastic for learning because there's a single place to look when something's wrong. Its downside only shows up once you compare it with the industrial pattern in the next section — the plugin knows nothing about real LIMO hardware, and its internals aren't reusable when you eventually plug in an actual motor controller.

student@limo-ws:~$ ros2 topic pub -1 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.2}, angular: {z: 0.0}}" student@limo-ws:~$ ros2 topic echo /odom --once pose: pose: position: {x: 0.0412, y: 0.0006, z: 0.0} twist: twist: linear: {x: 0.2, y: 0.0, z: 0.0} student@limo-ws:~$ ros2 run tf2_ros tf2_echo odom base_link Translation: [0.041, 0.001, 0.000] Rotation: in Quaternion [0.000, 0.000, 0.001, 1.000]

6.3ros2_control — the industrial pattern

The gazebo_ros plugin pattern is simple, but it doesn't scale to how real robotics companies build products. Industrial ROS 2 stacks almost always use ros2_control instead — a general framework built around three pieces:

PieceRole
controller_managerA process that loads controllers and hardware interfaces, and runs the real-time control loop
hardware_interfaceAn abstraction layer — can be backed by a simulated interface, or by a real serial/CAN driver talking to actual motors. The controller code above it never knows which.
Controllers (e.g. diff_drive_controller)Consume /cmd_vel, know the robot's wheel geometry, and issue per-joint commands through the hardware_interface

Which controllers to load, and at what update rate, is declared in a controllers.yaml file:

controller_manager:
  ros__parameters:
    update_rate: 50  # Hz

    diff_drive_controller:
      type: diff_drive_controller/DiffDriveController

diff_drive_controller:
  ros__parameters:
    left_wheel_names: ["left_wheel_joint"]
    right_wheel_names: ["right_wheel_joint"]
    wheel_separation: 0.172
    wheel_radius: 0.045
    cmd_vel_timeout: 0.5
flowchart TB A["/cmd_vel"] --> B["diff_drive_controller"] B --> C["controller_manager"] C --> D{"hardware_interface"} D -->|"simulated backend"| E["Gazebo physics"] D -->|"real backend, Lecture 9"| F["Serial / CAN link to real LIMO motors"] style B fill:#eef0ff,stroke:#3d4bf5,color:#211f1a,font-weight:bold style D fill:#f4effe,stroke:#8b5cf6,color:#211f1a,font-weight:bold style E fill:#eafaf3,stroke:#0e9e6e,color:#211f1a style F fill:#fdeee4,stroke:#c8622c,color:#211f1a
🌍 Why real robot companies use this

The engineering win is huge: you can develop and tune a diff_drive_controller entirely in Gazebo, then move to the real robot by swapping only the hardware_interface — from a simulated one to a real serial/CAN driver — with zero changes to the controller code. The same is true for arm controllers, gripper controllers, anything ros2_control manages. In Lecture 9 you'll meet LIMO's real embedded motion controller and see this swap happen for real — the diff_drive_controller you configure here does not need to be rewritten.

gazebo_ros plugin (6.2)ros2_control
Who talks to physicsThe plugin itself, directlyThe hardware_interface, behind an abstraction
Reusable on real hardware?No — Gazebo-only codeYes — same controller, different hardware_interface

⚠️ Don't conflate the two

This course's default LIMO simulation launch uses the simpler gazebo_ros plugin pattern from 6.2 — it is not running ros2_control underneath. If you go looking for a controller_manager node while running the default launch file, you won't find one; that's expected, not a bug.

6.4twist_watchdog.py — a safety habit worth keeping

limo_gazebosim/scripts/twist_watchdog.py is a small node with an outsized lesson. It tracks the timestamp of the last /cmd_vel message it received, and if no new command arrives within a timeout window, it publishes a zero Twist — bringing the robot to a stop.

flowchart LR A["/cmd_vel arrives"] --> B["Reset last-seen timer"] C["Timer check
(periodic)"] --> D{"Time since last cmd_vel
> timeout?"} D -->|"yes"| E["Publish zero Twist
(STOP)"] D -->|"no"| F["Do nothing — last command still valid"] style E fill:#fdeeec,stroke:#d64a3c,color:#211f1a,font-weight:bold 
# conceptual sketch, not a line-for-line copy of the real script
def timer_callback(self):
    elapsed = self.get_clock().now() - self.last_cmd_time
    if elapsed.nanoseconds / 1e9 > self.timeout_sec:
        self.cmd_vel_pub.publish(Twist())  # all-zero: stop
🔧 Why this matters far beyond LIMO

This is not a LIMO quirk — it's a pattern every teleoperated or scripted mobile robot needs. A dropped Wi-Fi link during joystick teleop, a control node that crashes mid-loop, a disconnected joystick USB cable — in every case, the last /cmd_vel the robot received might have been "drive forward at 0.3 m/s." Without a watchdog, the robot has no way of knowing the command is stale, and it will happily keep obeying it until it hits something. A robot's default on silence must be stopped, never "keep doing the last thing forever."

student@limo-ws:~$ ros2 run limo_gazebosim twist_watchdog.py --ros-args -p timeout_sec:=0.8 [INFO] [twist_watchdog]: watchdog started, timeout=0.8s [WARN] [twist_watchdog]: no /cmd_vel for 0.83s — publishing stop
🛠️ Where this becomes non-optional

In simulation, a watchdog failure just means LIMO drifts across an empty Gazebo floor. On the real robot (Lecture 9 onward) the exact same silent-network scenario means an unattended robot rolling toward a wall, a person, or a staircase at whatever speed it was last told. Build the habit now.

6.5Path-following, level 1 — bang-bang control

The rest of this session builds toward a real skill: driving LIMO to a target waypoint using only its current pose (from TF, tying directly back to Lecture 5) and a target Transform. We'll build three controllers of increasing sophistication, starting with the crudest one that actually works: on/off ("bang-bang") control.

The idea: compute the distance error and heading error to the goal. If either is above a threshold, command a fixed velocity. If below, stop. 

# trajectory_tracking_controller_on_off.py — core control law
dx = wx - x
dy = wy - y
distance_error = math.hypot(dx, dy)
angle_to_goal = math.atan2(dy, dx)
angle_error = angle_to_goal - theta   # then normalized to [-pi, pi]

# On/Off linear speed controller
if distance_error > 0.1:
    linear_speed = 0.2
else:
    linear_speed = 0.0

# On/Off angular speed controller
if angle_error > 0:
    angular_speed = 0.5
else:
    angular_speed = -0.5

motor_command = Twist()
motor_command.linear.x = linear_speed
motor_command.angular.z = angular_speed
self.publisher.publish(motor_command)
⚠️ Why it's jerky

There is no middle ground: the robot is always commanding full speed or zero, full left turn or full right turn. Near the goal, tiny fluctuations in the sign of angle_error flip angular_speed between +0.5 and -0.5 every control cycle, so LIMO visibly twitches and oscillates instead of settling. It also never manages final orientation at all — once distance_error < 0.1 it simply stops, facing whatever direction it happened to be facing.

Easy

Run the on/off controller against a single waypoint 1 metre straight ahead of LIMO's start pose. Watch /cmd_vel with ros2 topic echo /cmd_vel as it approaches — count how many times angular.z flips sign in the last 20 cm.

6.6Path-following, level 2 — proportional control

The obvious fix for jerkiness: instead of a fixed velocity, make the commanded velocity scale with the error. This is a classic proportional (P) controller — the same idea shows up everywhere from thermostats to cruise control. 

# trajectory_tracking_p_controller.py — core control law
distance_error = math.hypot(dx, dy)
angle_to_goal = math.atan2(dy, dx)
alpha = angle_to_goal - theta   # normalized to [-pi, pi]

Kp_linear = 0.5
Kp_angular = 1.0

linear_speed  = Kp_linear  * distance_error
angular_speed = Kp_angular * alpha

# clamp to the robot's speed limits
linear_speed  = max(min(linear_speed, 0.5), -0.5)
angular_speed = max(min(angular_speed, 1.0), -1.0)

v = kp_lin × distance_error and ω = kp_ang × heading_error. Far from the goal, the errors are large, so LIMO drives fast; as it gets close, both velocities taper smoothly toward zero instead of slamming to a stop.

🧠 Smoother, but still incomplete

This removes the twitchiness of bang-bang control — no more sign-flipping at full speed. But look at the control law again: it only ever drives alpha (heading toward the goal point) to zero. Nothing in this law cares what direction LIMO is facing once it arrives. Two robots with the same P controller, approaching the same goal from different directions, will stop at the same position but face completely different, uncontrolled headings.

⚠️ Tuning trap

It's tempting to push Kp_angular higher to make LIMO "snap" toward the goal direction faster. Push it too far and you re-introduce oscillation — the robot overshoots the correct heading, corrects, overshoots the other way, and the smooth P-controller behaviour degrades back toward bang-bang-like jitter. A gain that looks great on simple.world can already oscillate on potholes.world once RTF drops and control cycles get less regular.

Intermediate

Run the P controller toward a waypoint placed behind and to the side of LIMO's start pose (so it must turn substantially before advancing). Log the final heading with tf2_echo odom base_link once the robot stops, and compare it against the waypoint's own orientation field — confirm they do not match.

6.7Path-following, level 3 — pose regulation

To land at the goal and face the correct final orientation, we need a controller that reasons about three quantities instead of one. This is the classic unicycle pose-regulation formulation, using three errors usually named rho, alpha, beta:

  • ρ (rho) — straight-line distance from the robot's current position to the goal.
  • α (alpha) — the angle between the robot's current heading and the direction toward the goal (exactly the same quantity the P controller used).
  • β (beta) — the remaining orientation error once the robot reaches the goal: how far off the robot's final heading will be from the goal's desired orientation.
flowchart TB A["Current pose (x, y, theta)
from odom→base_link TF"] --> D["Compute rho, alpha, beta"] B["Goal waypoint (wx, wy, wtheta)
from /waypoint_cmd"] --> D D --> E["v = K_rho * rho"] D --> F["omega = K_alpha * alpha + K_beta * beta"] E --> G["/cmd_vel"] F --> G style D fill:#f4effe,stroke:#8b5cf6,color:#211f1a,font-weight:bold style G fill:#eafaf3,stroke:#0e9e6e,color:#211f1a,font-weight:bold

The control law itself is compact:

v     = K_rho   * rho
omega = K_alpha * alpha + K_beta * beta

Both terms driving omega matter: K_alpha * alpha steers the robot toward the goal point (same job as the P controller's angular term); K_beta * beta is the new piece — it continuously nudges the heading toward the goal's desired final orientation as well, so by the time rho reaches zero, the robot's heading has already converged too. 

# trajectory_tracking_kinematic_controller.py — core control law
dx = wx - x
dy = wy - y
rho = math.hypot(dx, dy)
angle_to_goal = math.atan2(dy, dx)
alpha = angle_to_goal - theta        # normalized to [-pi, pi]
beta = - theta - alpha               # normalized to [-pi, pi]

K_rho   = 0.4
K_alpha = 3.0
K_beta  = -0.5   # negative for stability

linear_speed  = K_rho * rho
angular_speed = K_alpha * alpha + K_beta * beta

linear_speed  = max(min(linear_speed, 0.5), -0.5)
angular_speed = max(min(angular_speed, 1.0), -1.0)
📖 Why K_beta is negative

This is a well-known stability result for this control law: for the closed-loop system to converge smoothly (rather than spiral or overshoot around the goal), the gains must satisfy K_rho > 0, K_beta < 0, and K_alpha - K_rho > 0. You don't need to re-derive this to use it — just remember that flipping K_beta positive by accident (an easy typo) will visibly break convergence near the goal.

ControllerReaches the goal positionReaches the goal orientationSmoothness
On/off (6.5)Yes, roughlyNo — arbitraryJerky, oscillates near goal
Proportional (6.6)Yes, smoothlyNo — arbitrarySmooth approach

Harder

Set a waypoint whose rotation field encodes a heading 90° different from the straight-line approach direction. Run all three controllers back to back against it and record, for each, the final heading error in degrees once the robot has stopped. Only the kinematic controller should land close to zero.

6.8Racing the referee

All three controllers above share the same shape: subscribe to /waypoint_cmd (geometry_msgs/msg/Transform), look up the current pose via TF, publish /cmd_vel. The trajectory_skeleton package gives you that shared scaffold — trajectory_tracking_controller.py — ready for you to drop your control law into. The trajectory_referee package plays the opposing role: it feeds waypoints along a named test route and scores how well you followed them.

flowchart LR A["trajectory_referee
trajectory_publisher"] -->|"/waypoint_cmd"| B["trajectory_skeleton
trajectory_tracking_controller"] C["odom → base_link TF"] --> B B -->|"/cmd_vel"| D["LIMO in Gazebo"] D -->|"pose feedback"| A A --> E["Score: dis or dor"] style B fill:#eef0ff,stroke:#3d4bf5,color:#211f1a,font-weight:bold style E fill:#eafaf3,stroke:#0e9e6e,color:#211f1a,font-weight:bold

Setup, once per workspace:

sudo apt install ros-humble-tf-transformations

Then, in separate terminals:

# terminal 1 — spawn LIMO + RViz
ros2 launch trajectory_skeleton view_robot.launch.py

# terminal 2 — your controller (edit this node with each level's control law)
ros2 run trajectory_skeleton trajectory_tracking_controller

# terminal 3 — the referee sends waypoints along a named route and scores you
ros2 run trajectory_referee trajectory_publisher route1 dis
📖 dis vs dor scoring modes

The second argument to trajectory_publisher selects what the referee scores: dis scores position only — how close you got to each waypoint's (x, y). dor scores position and orientation — it also checks how close your final heading was to the waypoint's target orientation. The on/off and P controllers can score reasonably under dis; only the kinematic controller should hold up well under dor.

6.9Summary, checkpoint & glossary

You moved from a black-box "the plugin drives the robot" understanding of simulation to seeing exactly how /cmd_vel becomes physics and physics becomes /odom and TF. You compared that simple pattern against the industrial controller_manager / hardware_interface / controller architecture that lets the exact same controller code run in Gazebo today and on real LIMO hardware in Lecture 9. You picked up a safety habit — the /cmd_vel watchdog — that belongs in every teleoperated robot you ever build. And you implemented, ran, and scored three path-following controllers of increasing sophistication, ending with a real pose-regulation controller that converges in both position and orientation.

Connection to the course

This session is the hinge between "LIMO exists in simulation" (Lectures 1–5) and "LIMO senses and reacts to its environment" (Lecture 7 onward: LiDAR, IMU, camera, obstacle avoidance). The pose-regulation controller you built here is also the direct ancestor of the path-following behaviour Nav2 will give you for free in later lectures — knowing how the rho/alpha/beta math works under the hood means Nav2's controller parameters will make sense instead of feeling like magic numbers. And the ros2_control pattern you learned in 6.3 is exactly what Lecture 9 swaps onto real hardware.

Real-Time Factor (RTF)
Ratio of simulated time elapsed to wall-clock time elapsed; RTF < 1 means the simulation is running slower than real life.
Plugin (gazebo_ros)
Code attached to a Gazebo model that reads/writes ROS 2 topics and directly manipulates the physics engine — here, the pattern that drives LIMO from /cmd_vel to /odom + TF.
controller_manager
The ros2_control process that loads hardware_interfaces and controllers and runs the control loop.
hardware_interface
An abstraction layer in ros2_control that can be backed by simulation or real hardware, without changing controller code.
Bang-bang control
A control strategy using only fixed, extreme output values (full on / full off) switched by a threshold — simple but prone to oscillation.
Proportional control
A control strategy where the output scales linearly with the current error, giving a smoother response than bang-bang control.
Pose regulation
The control problem of driving a robot to a target position and a target orientation, not just a target position.
rho / alpha / beta
The three errors in the classic unicycle pose-regulation formulation: distance to goal, heading-to-goal angle, and remaining final-orientation error.

Common Mistakes

  • Tuning Kp or K_alpha gains too aggressively, causing the robot to overshoot and oscillate around the goal heading instead of converging smoothly.
  • Forgetting that the TF lookup (odom → base_link) can throw a LookupException before the first odometry message has arrived — always wrap it in a try/except and skip the cycle rather than crashing the node.
  • Running two Gazebo worlds or two view_robot.launch.py instances at once and hitting port conflicts (Gazebo's default TCP port and the ROS 2 domain both collide) — always fully shut down one simulation before starting another.
  • Misreading dis vs dor scoring mode — celebrating a good dis score from the proportional controller without realizing the same run would score poorly under dor because orientation was never controlled.
